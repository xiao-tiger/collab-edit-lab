# CRDT Stage C1：最简 CRDT —— G-Counter 与 LWW-Register

> 前置：OT 篇（stage0~5）。CRDT 篇回答一个新问题：**没有中心服务器定序，凭什么还能收敛？**
> 本阶段先不碰文本，用两个最简单的数据结构把 CRDT 的数学直觉建立起来。

## 运行

无需服务器（这本身就是第一个教学点：P2P 也能收敛）——直接用浏览器打开：

```bash
npm run crdt:1   # 或 open crdt/01-counter-register/index.html
```

页面里模拟了两个对等节点（A / B），互发**整个状态的快照**做合并。

## 本阶段实现

### G-Counter（只增计数器）

```
状态：{ counts: { A: 2, B: 1 } }   ← 每个节点只改自己那一格
merge：对每一格取 max
```

每个节点只写自己的格子 → 格子之间天然无冲突；`max` 天然满足交换/结合/幂等。

### LWW-Register（最后写入者胜寄存器）

```
状态：{ value, n: 逻辑时钟, by: 写入者 }
merge：n 大者胜；n 并列按 by 字典序裁决
```

永不发散，但**并发写会丢一个**（last-writer-wins）。这个"丢"就是 C2 文本 CRDT 要解决"不丢字符"的动机。

### 设计要点：状态里不放"我是谁"

节点身份属于副本（replica），不属于 CRDT 状态。如果把 nodeId 放进状态，merge 结果会依赖操作数顺序，交换律在对象层面就不严格成立（我们的自动化测试真抓到过这个问题）。

## 核心认知：三条数学性质

CRDT 不靠定序，靠 merge 是纯函数且满足：

| 性质 | 含义 | 抵御的网络问题 |
|---|---|---|
| 交换律 | merge(a,b) = merge(b,a) | 消息乱序 |
| 结合律 | merge(merge(a,b),c) = merge(a,merge(b,c)) | 分批合并、拓扑任意 |
| 幂等 | merge(a,a) = a | 重复投递 |

## 实验

1. **基本同步**：两边点 +1、写寄存器 → 两端状态收敛一致
2. **勾上"重复投递"**：同一快照送两次 → 计数器不多算（幂等的直观体现）
3. **勾上"乱序/大抖动"**：消息乱跳 → 最终依然一致
4. **切到"朴素覆盖"模式**：两边同时快速点 +1 → 计数丢增量、两端发散 ❌ —— 这就是没有 CRDT 的世界（呼应 OT 篇 Stage 0 的互相覆盖）

## 已知局限

- 计数器只能增（要减需要 PN-Counter：两个 G-Counter 一增一减，同理）
- 寄存器并发写会丢（LWW 取舍）
- 都是玩具粒度——**文本需要的是"每个字符都可合并"**，这正是 C2 的 RGA
