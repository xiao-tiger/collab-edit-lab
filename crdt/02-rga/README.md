# CRDT Stage C2：迷你 RGA —— 文本 CRDT（真服务端版）

> 前置：C1（merge 三性质）。本阶段把 CRDT 用到文本上——这是整个 CRDT 篇的核心，约 80 行核心算法。

## 运行

```bash
npm run crdt:2   # 或 node crdt/02-rga/server.js → http://localhost:8012
```

**每个浏览器标签页 = 一个节点**（随机节点 id，即字符 id 的前缀），多开互玩。

## 架构

与 C1 同款：服务端只做**中转 + 存档副本**（存档 = 一个 merge 了所有快照的 RGA），不定序、不裁决。协议就一种数据消息：

```js
{ type: 'snapshot', from: 节点id, items: [全部 Item] }   // 另：连上时服务端发 {type:'init', items}
```

## 文件结构（三层分离）

| 文件 | 层 | 职责 |
|---|---|---|
| `server.js` | 服务端 | 静态服务 + 中转 + 存档副本（~60 行） |
| `public/rga.js` | 算法层 | RGA：Item、插入/删除、并集合并、序列重建（ESM；canonical 版本） |
| `public/client.js` | 数据层 | 本节点状态 + diff 翻译 + ws 收发（五段直线结构） |
| `public/app.js` | 渲染层 | textarea 绑定、Item 结构（墓碑）渲染 |
| `public/index.html` | 结构 | 页面骨架与样式 |

## 核心思想：给每个字符发"身份证"

```js
Item = {
  id: 'N-3X9K:3',  // 节点id + 计数器，全局唯一、可比较
  left: 'N-7Q2M:5',// 我插入时左边那个字符的 id
  ch: 'X',
  deleted: false,  // 删除 = 打墓碑，不物理移除
}
```

- **合并**：按 id 求并集（墓碑"删过即删"）——三性质由并集天然保证
- **重建文本**：从根 DFS；同一 `left` 的并发兄弟按 id **降序**（"后来者居左"，否则开头打字落位错误）

## 与 OT 的对照

| | OT（stage3） | RGA（C2） |
|---|---|---|
| 定位 | 相对位置 pos | 绝对身份 id |
| 并发修正 | transform + 中心定序 | 不需要——不存在"过期" |
| delete × 并发 insert | **吸收**（插入被删） | **插入存活** |
| 乱序/重复 | 需要定序保证 | 天然免疫 |
| 代价 | 需要中心服务器 | 墓碑膨胀、每字符元数据 |

## 实验

1. 两个标签页同时打字 → 文本与**内部结构**都收敛（页面下方有每个 Item 的 id 上标，删除线是墓碑）
2. 勾"随机延迟（乱序）"/"重复发送" → 毫无影响
3. A 删一段的同时 B 往里打字 → B 的字**存活**（对照 OT 的吸收规则）
4. 先在一个标签页打字，再开新标签页 → 通过 init 存档追上进度

## 已知局限

1. **交错问题**：两站点交替并发插入同一位置，可能交错（Yjs 的 YATA 解决）
2. 墓碑只增不减（真实系统靠 GC/压缩）
3. 状态型每次发全量 Item；生产用增量同步（Yjs 的 sync step）
