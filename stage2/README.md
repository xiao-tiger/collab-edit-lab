# Stage 2：版本号 + 服务端全局定序

## 运行

```bash
node stage2/server.js   # 端口 8002，开两个浏览器标签页访问
```

## 本阶段实现

- **`rev`**：服务端文档版本号，每接受一个操作 +1，递增值即全局顺序（中心化定序）
- **`baseRev`**：客户端操作声明"我基于版本 N 算出"，服务端据此判断新鲜（接受）或过期（拒绝）
- **`history`**：服务端按序保存全部已接受操作（Stage 3 做 transform 的数据基础）
- **回执 + 一个在途操作**：客户端任何时刻最多一个未确认操作，其余排队，保证 `baseRev` 诚实、单人连打不丢字
- **冲突策略**：过期操作被拒绝，服务端回传权威全文，客户端强制重同步——**系统永不发散**

## 已知弊端

1. **冲突丢编辑**：被拒绝方的 pending 和排队操作整批丢弃，用户体验差
2. 收敛靠"丢弃 + 全量重同步"兜底，是**恢复**不是**合并**；客户端对有在途操作时到达的远端操作也只是直接套用，靠随后的拒绝来擦屁股
3. 拒绝时服务端其实**已经知道**对方错过了哪些操作（`history[baseRev..rev-1]`），但还不会利用

## 后续阶段如何解决

- **Stage 3**：服务端用 `transform()` 把过期操作针对它错过的操作逐个修正坐标后再应用——冲突不再丢编辑
- **Stage 4**：客户端补齐对称的变换逻辑（本地未确认操作 vs 远端新到操作），成为完整的 OT 协议
