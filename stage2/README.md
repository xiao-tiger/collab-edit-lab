# Stage 2：版本号 + 服务端全局定序

> 本阶段解决 Stage 1 的"静默发散"：给文档加版本号，让冲突**可检测、可恢复**。
> 代价是冲突时丢编辑——这个"痛"正是 Stage 3 要消除的。

## 运行

```bash
node stage2/server.js   # 端口 8002，开两个浏览器标签页访问
```

## 本阶段实现

### 四个核心概念

**`rev`（服务端）**：文档版本号，每接受一个操作 +1。递增值即**全局顺序**——所有操作在服务端被排成唯一的一条线，这就是"中心化定序"。

**`baseRev`（客户端 → 服务端）**：操作声明"我是基于版本 N 的文档算出来的"。注意它是**全局 rev 在客户端眼中的快照**，不是各客户端自己的计数器：

```
初始：服务端 rev=0，A.rev=0，B.rev=0
A 发出 { op, baseRev=0 } → 0===0 ✅ 接受，rev=1，广播
A 收到回执 → A.rev=1；B 收到广播 → B.rev=1   ← 又对齐了
```

平时 `baseRev` 总能匹配上，因为每个被接受的操作都会广播给所有人、拉齐版本。
**匹配不上恰好标志"真并发"**：

```
服务端 rev=5，A、B 同时敲字，都发出 baseRev=5
A 先到：5===5 ✅ 接受，rev=6
B 后到：5!==6 ❌ 过期 —— B 算坐标时没见过 A 的操作，坐标不可信
```

**`history`（服务端）**：按序保存全部已接受操作。拒绝时服务端**精确知道**对方错过了哪些操作（`history[baseRev..rev-1]`）——Stage 2 还不会利用这个信息，Stage 3 全靠它。

**一个在途操作 + 排队（客户端纪律）**：任何时刻最多一个未确认操作，其余进 buffer，收到回执再发下一个。为什么必须这样？否则快速连敲 3 个字会发出 3 个相同 `baseRev` 的操作，第 2、3 个被误伤拒绝——这不是并发冲突，只是自己的回执还在路上。排队保证 `baseRev` 永远等于"我真实见过的最新版本"，**过期一定意味着真并发**。

### 冲突策略：拒绝 + 强制重同步

过期操作被拒绝，服务端回传权威全文，客户端丢弃 pending + buffer 并整体刷新。
**服务端是唯一真理源，所以系统永不发散**；代价是冲突时用户的编辑被整批抹掉（红色警告条可见）。

## 实验

1. **并发实验**（延迟勾着）：A 开头敲 `A`，B 末尾删 `d` → 后到一定收到红色警告，编辑被丢弃，但两边校验值相同（收敛！对比 Stage 1 的静默发散）
2. **单人快速打字**（延迟勾着）：日志里"发送 → 回执 → 发送"流水作业，一个操作都不丢——这就是"一个在途操作"纪律的作用

## 已知弊端

1. **冲突丢编辑**：被拒绝方的 pending 和排队操作整批丢弃，体验差
2. 收敛靠"丢弃 + 全量重同步"兜底，是**恢复**不是**合并**
3. 客户端对"有在途操作时到达的远端操作"只是直接套用，靠随后的拒绝擦屁股（Stage 3 才会正确变换）

## 后续阶段如何解决

- **Stage 3**：服务端用 `transform()` 把过期操作针对 `history` 逐个修正坐标后再应用——冲突不再丢编辑
- **Stage 4**：边界情况验证、光标 transform
