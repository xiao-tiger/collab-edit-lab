# Stage 4：打磨 —— 光标 transform + 远端光标 + 压力测试

> 前置：Stage 3（transform）。本阶段不动算法，把 OT 能力扩展到「光标」这类瞬时状态，并用自动化压力测试验证高压下的收敛性。

## 运行

```bash
npm run ot:4   # 或 node ot/04-cursor-stress/server.js   # 端口 8004，开两个浏览器标签页访问
```

## 本阶段实现

### ① 光标换算（`transformPos`）：替代朴素光标调整

Stage 1 以来的"光标修正"是手写的朴素规则（insert 在光标前就 +len）。其实光标换算不用单独写——**把光标看成一个空串 insert，直接复用 transform**：

```js
function transformPos(pos, op) {
  return transform({ kind: 'insert', pos, str: '' }, op, false).pos;
}
```

- 删除区间覆盖光标时，transform 的"作废"返回值恰好把光标夹在删除起点——白送的正确行为
- **`opIsLeft` 恒为 `false`**：同位置并发插入时光标跟随后到文本。裁决方向两端必须全局一致（一边"光标不动"、另一边"光标被推走"，双方看到的光标就错位了）——和操作的同位置裁决是同一个道理

### ② 远端光标同步

光标是和操作平级的另一类消息：`{ type:'cursor', pos, baseRev, from }`。**不定序、不进 history**，纯瞬时状态。但它同样有过期问题，修正分两段：

1. **服务端**：收到 `baseRev` 过期的光标，针对 `history[baseRev..rev-1]` 逐个修正再转发
2. **客户端**：收到后若本地还有未确认操作（pending/buffer），再针对它们换算一次——因为本地文档 = 服务端文档 + 我的未确认操作

编辑器下方的"文档镜像"把双光标渲染出来：蓝线是我，橙线是对方。

### ③ 机器人压力测试

点「🤖 机器人压力测试」：以 70ms 间隔随机插入/删除共 80 次，**走的是和真人输入完全相同的链路**（改 textarea → 触发 input 事件 → diff → 发送）。两个标签页同时启动，跑完等"在途/排队"清零，对比校验值——高并发乱序下必然一致，这才是 OT 正确的硬证据。

## 实验

1. **远端光标**：两个标签页，A 随便点/打字 → B 的镜像里橙线实时跟随；勾上延迟并发操作，观察服务端日志的 `[光标修正]`
2. **光标不被拍飞**：A 把光标放在文档中间，B 在 A 光标前打字 → A 的光标平滑右移，继续打字不断流
3. **压力测试**：两个标签页都点机器人按钮 → 跑完对比校验值相同

## 已知简化（教学取舍）

1. 远端光标只在**收到消息时**换算一次；此后我本地继续打字，对方光标显示会漂（对方下次动光标时纠正）。生产系统会在每次本地变更后重换算
2. 只处理 collapsed 光标；选区换算同理（对 selectionStart/End 各做一次 transformPos，代码里其实已支持）
3. 压力测试只做随机单字符粒度操作
