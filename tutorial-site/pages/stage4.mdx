# Stage 4 · pending、buffer 和光标怎样修正

为了让输入没有网络延迟，客户端会立即把本地操作应用到编辑框，再把它作为 `pending` 发给服务端。快速继续输入时，后续操作进入 `buffer`。

```text
本地文档 = 服务端已确认状态 + pending + buffer
```

因此远端操作不能直接应用到本地文档。它必须穿过 pending 和 buffer；与此同时，本地未确认操作也要针对远端操作做对称变换。

## 逐步观察客户端双侧变换

先观察 pending/buffer，再切换到远端光标。算法区会显示远端操作和本地操作怎样同时更新。

## 为什么只能有一个 pending

如果连续三次输入都立刻发送，它们可能都携带同一个 `baseRev`，然后被自己的前一个操作变成过期消息。

正确流水线是：

```text
本地输入 → pending → 等待回执
后续输入 → buffer
pending 收到回执 → 从 buffer 取下一条发送
```

## 光标为什么也要 transform

光标位置同样是数字坐标。可以把光标看成一次插入空字符串的位置：

```js
function transformPos(pos, op) {
  return transform(
    { kind: 'insert', pos, str: '' },
    op,
    false,
  ).pos
}
```

光标、选区、在线名单属于临时 Presence，不进入文档 `history`；但过期坐标仍然需要经过服务端历史和客户端 pending 两段修正。

## 本章答案

OT 不只是服务端 transform。客户端必须维护 pending/buffer，对远端操作和本地未确认操作做双侧变换，才能让“本地立即显示”和“最终权威顺序”同时成立。
