## 生产化清单

**光标 transform**：远端操作到达时，本地选区也要按同样规则换算（教程 demo 里只是朴素调整）。多人产品时还要广播彼此的光标/选区做展示。

**compose / 批量**：排队操作逐个发送，每 RTT 一个，高延迟下积压。真实系统会把相邻操作 compose 成一个再发。

**持久化**：操作日志 + 定期快照。新加入者读快照再增量同步，不从头回放百万条操作。

**协同 undo**：只能撤销「我自己的」操作，且要基于他人已插入的内容生成逆操作——比单机 undo 难一个量级。

**富文本**：纯文本 OT 升级为树结构 OT（段落/样式节点），「delete 吸收」这类取舍才有真正的解。

**横向扩展**：按文档分片——每个文档一个权威进程管 rev 定序，百万文档分摊到海量机器。单文档并发上限几十人，从来不存在「百万用户一个文档」。

## OT vs CRDT：什么时候换路线

| | OT | CRDT |
|---|---|---|
| 定序 | 中心化（服务端权威） | 无需中心，数学合并 |
| 离线多天合并 | 痛苦 | 天然支持 |
| P2P / 端到端加密 | 服务端要看懂内容才能 transform | 天然支持 |
| 元数据开销 | 无 | 每字符带 ID、删除留墓碑 |
| 代表 | Google Docs、ShareDB | Yjs、Automerge、Figma（自研） |

结论：中心化产品用 OT 足够好；需要离线/P2P/加密时选 CRDT。
