# Stage 2 · 版本号 + 服务端全局定序

给文档加版本号：服务端给每个操作分配递增 `rev`（全局唯一顺序）；操作必须声明 `baseRev`——我是基于哪版文档算的。冲突从此**可检测、可恢复**，代价是丢编辑。

## 四个核心概念

**`rev`（服务端）**：每接受一个操作 +1，递增值即全局唯一顺序（中心化定序）。

**`baseRev`（客户端→服务端）**：操作声明「我是基于版本 N 的文档算出来的」。注意它不是各客户端自己的计数器，而是**全局 rev 在客户端眼中的快照**：

```
初始：服务端 rev=0，A.rev=0，B.rev=0
A 发出 { op, baseRev=0 } → 0===0 ✅ 接受，rev=1，广播
A 收到回执 → A.rev=1；B 收到广播 → B.rev=1   ← 又对齐了

A、B 同一瞬间敲字，都发 baseRev=1：
  先到者：1===1 ✅ 接受，rev=2
  后到者：1≠2 ❌ 过期 —— 你算坐标时漏看了别人的操作
```

平时总能对上（广播会拉齐版本）；**对不上的瞬间恰好就是真并发**——版本号把静默发散变成了可检测事件。

**`history`（服务端）**：按序保存全部已接受操作。拒绝时服务端精确知道对方错过了哪几个操作（Stage 3 全靠它）。

**一个在途操作**：客户端任何时刻最多一个未确认操作，其余排队，收到回执再发下一个。否则连敲 3 个字会发出 3 个相同 baseRev 的操作，被自己的回执误伤。

## 冲突策略：拒绝 + 强制重同步

```js
if (msg.baseRev === rev) { /* 接受、定序、广播 */ }
else { /* 拒绝，回传权威全文，客户端强制重同步 */ }
```

服务端是唯一真理源，所以系统**永不发散**；但冲突时用户的编辑被整批丢掉。

## 小结

**✅ 学会了什么**：rev / baseRev / history 三件套；中心化定序 = 唯一时间线；一个在途操作的流水线纪律。

**⚠️ 还有什么问题**：冲突丢编辑，体验灾难；是「恢复」不是「合并」；服务端手握 history 却不会利用。
