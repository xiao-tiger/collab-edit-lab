## 这两个数据结构是干什么的

它们不是玩具，是两类真实场景的**最小模型**：

**G-Counter（只增计数器）** —— 对应"点赞数、阅读量"这类只增场景。
痛点：两个节点同时 +1，如果同步的是"当前值"，互相覆盖必然丢一次（就是 OT 篇 Stage 0 的互相覆盖）。
CRDT 解法：**每个节点只改自己那一格**（`counts: {A: 2, B: 1}`），合并时每格取 `max`。格子之间天然无冲突，所以永远收敛，且一次都丢不了。

**LWW-Register（最后写入者胜寄存器）** —— 对应"用户名、配置项"这类单值场景。
解法：每次写带上逻辑时钟 `n`，合并时 **n 大者胜**；n 并列按写入者 id 裁决。
注意代价：**并发写会丢一个**（last-write-wins）。对配置项可以接受，对文本完全不能接受——两个人同时改一句话，总要没了一个人的？这正是 C2 要解决"不丢字符"的动机。

## merge 的作用：让网络层可以"随便烂"

没有 merge 时（沙盒里的"朴素覆盖"对照组），同步 = 用对方的状态覆盖自己 → 并发必丢、乱序必乱。

有了 merge 后，同步变成一句话：**把当前状态发给对方，对方 merge 进来**。因为 merge 是纯函数且满足三条数学性质，网络层怎么捣乱都不怕：

| 性质 | 含义 | 抵御的网络问题 |
|---|---|---|
| 交换律 | merge(a,b) = merge(b,a) | 消息乱序 |
| 结合律 | merge(merge(a,b),c) = merge(a,merge(b,c)) | 分批合并、拓扑任意 |
| 幂等 | merge(a,a) = a | 重复投递 |

> **设计要点**：状态里不放「我是谁」。节点身份属于副本，不属于 CRDT 状态——否则 merge 结果依赖操作数顺序，交换律在对象层面就不严格成立（自动化测试真抓到过这个问题）。

## 小结

**✅ 学会了什么**：merge 三性质；状态型同步 = 发快照 + 纯函数合并；G-Counter（只增场景不丢）、LWW-Register（单值场景会丢）各自的适用面。

**⚠️ 还有什么问题**：计数器只能增；寄存器并发写会丢一个——文本忍不了。
