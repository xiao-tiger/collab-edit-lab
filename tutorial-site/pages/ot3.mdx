# O3 · 服务端怎样发现过期坐标

服务端为每个被接受的操作分配递增版本 `rev`。客户端发送操作时，必须声明自己基于哪个版本计算坐标：`baseRev`。

```js
{
  op: { kind: 'delete', pos: 3, len: 1 },
  baseRev: 0,
}
```

如果消息到达时服务端已经是 `rev=1`，说明这条操作至少错过了一个修改，它的坐标不能直接使用。

## 逐步观察检测和拒绝

默认场景中 A、B 都基于 `rev=0` 操作。A 先被接受后，B 的 `baseRev=0` 与服务端 `rev=1` 不再相等。

## 四个核心状态

```text
server.rev    权威文档当前版本
baseRev       客户端生成操作时看到的版本
history       服务端按顺序保存的已接受操作
pending       客户端已发送但尚未确认的操作
```

为了避免客户端连续输入产生多个相同 `baseRev` 的消息，任何时刻只发送一个 `pending`；后续操作先进入 `buffer`，收到回执后再发送。

## 本章答案

`baseRev !== server.rev` 能可靠发现旧坐标。拒绝和 resync 保证系统不再发散，但只是恢复权威状态，并没有保留被拒绝的用户意图。

## 留给下一章的问题

服务端已经保存了操作错过的 `history`。能不能利用这些历史，把旧坐标换算到当前版本后继续接受？这就是 transform。
