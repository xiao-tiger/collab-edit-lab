# Stage 0：最笨的协同 —— 全量文本广播

> 本阶段是整个系列的起点：用最直觉的方式做协同，**亲手把 bug 复现出来**，
> 建立"为什么需要 OT/CRDT"的问题感。

## 运行

```bash
node stage0/server.js   # 端口 8000，开两个浏览器标签页访问
```

## 本阶段实现

- WebSocket 双向通道；服务端内存保存整篇文档（一个大字符串）
- 客户端每次输入，把**整篇文档**发给服务端；服务端全量覆盖并广播给其他人
- 新加入者连上时拿到当前全文
- 冲突策略：**last-write-wins（后到者胜）**——谁的消息后到，谁的整篇文档成为"真相"

## 为什么会出问题（核心实验）

开两个标签页，同时快速打字。假设文档是 `"abc"`，同一瞬间：

```
A 在末尾敲 X → A 本地 "abcX" → 发出全量 "abcX"
B 在开头敲 Y → B 本地 "Yabc" → 发出全量 "Yabc"

正确结果应该是 "YabcX"，但实际：
  A 收到 "Yabc" → 自己的 X 被抹掉
  B 收到 "abcX" → 自己的 Y 被抹掉
→ 两个更新互相覆盖，各丢一个字，两边还不一致（发散）
```

同时还会观察到：对方的消息到达时，**自己的光标被拍飞到末尾**（直接覆盖 `textarea.value` 会重置选区）。

## 根因分析

全量文本不携带**意图**。"在位置 3 插入 X" 和 "整篇变成 abcX" 信息量完全不同：

- 前者可以和别人的并发操作**合并**
- 后者只能和别人的整篇**互相覆盖**

## 已知弊端

1. 并发互相覆盖、丢字、发散且无法察觉
2. 光标被拍飞
3. 服务端不知道用户改了哪里，无从合并

## 后续阶段如何解决

- **Stage 1**：引入操作模型（insert/delete），解决覆盖丢字，并做朴素光标修正
- **Stage 2**：引入版本号，让发散变得**可检测**
